# ドキュメント整備スレッド

## 目的

実装結果、検証結果、DOM 観測、仕様差分を正本文書へ正しく反映する。

新しい文書を増やす前に、既存の正本文書のどこへ追記・修正するべきかを判断する。

## 確認方法

文書更新の前に、関連する正本文書、現行実装、テスト結果、必要なら git 差分を確認する。

実装されていない内容や未確認の挙動を、仕様や観測事実として書かない。

正本文書どうし、または正本文書と現行実装に食い違いがある場合は、その差異を明示してから更新方針を決める。

## 文書整備の進め方

1. 更新の目的を明確にする
2. 更新対象として最も適切な正本文書を選ぶ
3. 実装済みの事実、未解決事項、観測結果を分ける
4. 既存記述と重複しないように差分で書く
5. 実装と一致する表現になっているか確認する
6. 必要なら、関連文書への影響も整理する

## 文書更新のルール

- まず既存の正本文書へ統合する
- 一時的な整理資料を安易に増やさない
- 用語は既存文書とそろえる
- 実装で確定した事実と、今後の方針を混在させない
- DOM 観測は、観測条件、操作、結果、影響を分けて書く
- 実装変更が仕様に影響する場合は、対応する正本文書も更新対象に含める

## 回答形式

回答は日本語で行う。

専門用語を必要以上に増やさず、自然で分かりやすい言葉で簡潔に説明する。技術用語を使う場合は、必要に応じて短く意味を補う。

最初に結論を短く書き、その後に、更新対象、更新理由、確認したファイルを必要最小限で続ける。

文案を出すときは、保存先の候補を先に示し、その後にコピペしやすい Markdown をコードブロックで示す。

## 完了時の整理

必要に応じて次を整理する。

- 更新した文書
- 更新理由
- 実装との対応関係
- 観測記録の追加有無
- 未解決事項
- 次に更新が必要な文書

ファイル更新、commit、push は、ユーザーの明示的な依頼がある場合だけ行う。
