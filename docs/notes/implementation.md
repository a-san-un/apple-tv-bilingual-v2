# 実装スレッド

## 目的

正本文書と現行実装に沿って、対象範囲を絞って実装を進める。

1回の作業は小さく区切り、責務境界、cleanup、安全な検証を保ちながら進める。

## 作業開始時の確認

実装前に、現行状態を確認する。

- `git status -sb`
- `git log --oneline -n 10`
- `git ls-files`

未コミット差分、想定外の変更、正本文書と現行実装の不一致があれば、実装前に報告する。

## 実装前の確認

対象作業に関係する正本文書、現行実装、型定義、既存テストを確認してから変更する。

ファイル内容、関数名、責務、行番号、既存挙動を、未確認のまま断定しない。

変更案を出す前に、現行コードの対象部分を確認する。

## 残作業一覧表

各ターンの**実装作業開始前**と**終了後**に、残作業一覧表を必ず表示する。

一覧表では、少なくとも次を含める。

- 今回の目的
- 現在の作業単位
- 完了済み
- 進行中
- 未着手
- 進められない理由
- このターンで扱う範囲
- 次ターンの候補

表示は簡潔でよいが、毎回更新する。  
新しい事実、仕様差分、テスト失敗、実機確認結果が出た場合は、その内容を反映して更新する。

表示例:

```md
| 項目 | 内容 |
|---|---|
| 今回の目的 | Phase 4 の subtitle source 実装 |
| 現在の作業単位 | source の購読開始・cleanup 整備 |
| 完了済み | resolver の型整理、既存依存の確認 |
| 進行中 | cue 購読ロジック |
| 未着手 | unit test 追加、実機確認 |
| 進められない理由 | なし |
| このターンで扱う範囲 | source 本体の最小実装 |
| 次ターンの候補 | test 追加、build 確認 |
```

## 実装の進め方

1. 今回の目的と対象範囲を明確にする
2. 関係する仕様と現行実装を確認する
3. 残作業一覧表を表示する
4. 変更対象を最小単位に絞る
5. 責務を混在させず、owner を明確にして実装する
6. 先に cleanup と failure path を確認する
7. 型、テスト、呼び出し側への影響を確認する
8. 実装後に検証結果をまとめる
9. 更新した残作業一覧表を再表示する

## 実装時のルール

- coordinator に詳細ロジックを入れすぎない
- resource を登録した module が cleanup の owner を持つ
- listener、timer、observer、binding、DOM の owner を曖昧にしない
- 既存版は調査対象として扱い、そのままコピーしない
- 複雑な回避策は、必要性が確認できるまで持ち込まない
- 対象外の責務まで広げない

## テストと検証

実装後は、対象に応じて型検査、lint、test、build を実行する。

実行したコマンド、成功したもの、失敗したもの、失敗時の内容を明示する。結果が未確認なら、未確認と書く。

実機確認が必要な項目は、再現条件、操作、結果を分けて整理する。

## 回答形式

回答は日本語で行う。

専門用語を必要以上に増やさず、自然で分かりやすい言葉で簡潔に説明する。技術用語を使う場合は、必要に応じて短く意味を補う。

最初に結論を短く書き、その後に、変更内容、確認したファイル、検証結果を必要最小限で続ける。

ファイルに触れる回答では、確認した正本文書・現行実装・テストを明示する。

## 完了報告

完了時は、必要に応じて次を報告する。

- 目的と実施内容
- 変更したファイル
- 責務境界や影響範囲
- 実行した検証コマンドと結果
- 実機確認の有無と結果
- 未解決事項
- 文書更新が必要な点

commit、push、ファイル削除は、ユーザーの明示的な依頼があるまで行わない。
